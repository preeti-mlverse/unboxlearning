How to build the engine behind the website

What the website promises, what already exists in the code, what's missing, and the order to build it in. Grounded in the current codebase at github.com/preeti-mlverse/unboxlearning.

In short: don't build every feature at once. Build one complete loop for real people first, then widen it.

  1. Foundations: accounts, a real database, a server, and quality and cost checks.
  2. The core loop, made solid: an educator unboxes a chapter, reviews it and shares it, and learners complete it.
  3. The learner model: what each learner knows, what they're forgetting, which misconceptions they hold.
  4. Adaptation and educator analytics, built on that learner model.
  5. Breadth: voice, languages, simulations, role-play, then LMS integrations.

About half of what the website shows already works in some form. The plan below turns that into a product a pilot school can use, in roughly 5–6 months with one developer working with an AI coding assistant.

2. The shape of the engine

Seven layers, each with one job. The content graph in the middle is the contract every other part reads and writes; the learner model is the second one. Most of the work below is about strengthening these two.

1 · IngestAny file or link → clean, structured text, tables, figures and transcripts, with page and timestamp references
2 · Content graphConcepts, relationships, prerequisites, examples, misconceptions, each traced to the source passages
3 · Learning designGoal and audience → outline → for each concept, the right format: card, game, simulation, role-play, voice lesson
4 · Generation and checksStructured AI output, then automatic checks: reading level, answer keys, fact-check against the source, human review
5 · DeliveryLearner app, tutor, voice, languages, sharing, classes, LMS packages
6 · Learner modelEvery answer becomes evidence: mastery per concept, memory strength, misconceptions, time spent
7 · Adaptation and analyticsWhat each learner sees next, reviews timed to memory, and the educator dashboard
Across all layersAccounts and organisations · AI provider gateway with cost caps · job queue · file storage · privacy and security · quality test sets · usage and impact logging

3. How to build it well

One complete loop before breadth

A real educator and a real class using one chapter end to end beats ten half-finished features. Every phase ends with real people using it.

Measure quality from day one

Keep a fixed set of 10 test sources across subjects and languages. Every change runs against it: card quality, fact-check flags, cost per course, tutor answers.

Record evidence for the grant as you go

Log every learning event in a standard format (xAPI style) from the first pilot. Mastery gains and retention are what reviewers will ask for later.

Use proven parts, build the core

Use existing tools for accounts, the database, spaced repetition and LMS packaging. Spend your own effort on the content graph, learning design and learner model.

Keep claims honest

Label features "live", "in pilot" or "coming" on the website and in grant documents. Promise the loop you can show; describe the rest as the roadmap.

Control cost and privacy early

A spending cap per course and per learner, Indian hosting for learner data, and consent for children's data under India's DPDP Act, before the first school pilot.

4. The build sequence

Weeks assume one developer working with an AI coding assistant. Phases 0–3 make a pilot-ready product (about 13 weeks); phases 4–6 add the differentiators.

0

Foundations

2 weeksneeds the new server
  • Server at app.unboxlearning.in: the app, a PostgreSQL database, file storage, automatic HTTPS
  • Accounts and roles (learner, educator, admin) and organisations; connect the website's sign-up and log-in
  • Background job queue for course building; spending caps per course
  • Quality test set: 10 sources (science, history, maths, a policy, a video, Hindi material) with a scoring sheet
  • Automatic tests and deployment on every change

Done when: an educator signs up on unboxlearning.in, logs into the app and builds a course, and every change is tested before going live.

1

The core loop, made solid

3–4 weekspilot with 2–3 educators
  • Unbox it: upload → understand → outline → generate → review → publish, reliable on the test set
  • Classes: an educator creates a class, assigns a course, learners join with a code
  • "Where is this from?" on every card; the educator sees the source passage behind each card
  • Better scanned-PDF and maths handling (docling); stronger prerequisite links in the concept graph

Done when: pilot educators turn their own material into courses, fewer than 1 card in 20 needs a fix, and a course costs under ₹15 to build.

2

The learner model

3 weeksfirst class pilot
  • Every answer, hint, tutor question and time spent is recorded as a learning event
  • Mastery per concept (BKT, moved from the older app); spaced reviews with FSRS and simple reminders
  • Assessment that teaches: tag likely misconceptions, give a hint, let the learner retry, update mastery
  • Tutor remembers the learner's weak concepts; a tutor test set (does it ever give the answer away? stay on source?)

Done when: a class uses a course for two weeks, and you can show each learner's mastery by concept and what they still remember a week later.

3

Adaptation and the educator dashboard

3 weeksfirst impact numbers
  • Path rules: skip what's mastered, add a worked example when nearly there, a simpler explanation or a prerequisite when there's a gap
  • Educator dashboard: mastery by concept, common misconceptions, drop-off points, learners who need help
  • Pre-test and post-test per course to measure learning gain (the evidence module exists in the older app)

Done when: two learners with different answers get different paths through the same course, and the pilot shows a measurable pre/post gain. This is the evidence for the grant.

4

Voice and languages

3–4 weeks
  • Natural spoken conversation with the tutor, including interruptions, using a real-time voice AI service
  • Explanations adapted per language and level, not just translated; a glossary so terms stay consistent
  • Native-speaker review of Hindi and one more Indian language; speaking practice for language courses
  • Low-data mode and an installable phone app (PWA)

Done when: a learner can complete a module mostly by voice in Hindi, and a native speaker rates the explanations as natural.

5

Learning you can touch

4 weeks
  • A library of 8–10 interactive widgets: sliders on a formula, cause and effect, sorting, building a diagram, graph exploration, timelines
  • The engine picks a widget when a concept suits it and fills in its settings from the source; the educator can preview and change it
  • Role-play scenarios inside micro-courses, with feedback against a rubric

Done when: on the test set, at least one in three science or economics modules gets a working simulation without hand-coding.

6

Integrations and scale

3–4 weeks
  • SCORM and cmi5 packages; xAPI tracking; LTI 1.3 for Moodle and other learning platforms
  • Organisation admin: many classes, many educators, usage and cost reports
  • Later: marketplace, paid courses, more languages

Done when: a course runs inside a school's Moodle and reports scores back.

6. For the grant submission

  • Present as working now: unbox any material into a micro-course, source-checked cards and games, the tutor, narration, translation, sharing by link.
  • Present as the pilot plan: phases 1–3, with the measures you'll report: mastery gain from pre-test to post-test, retention after a week, educator time saved, cost per course.
  • Present as the roadmap: voice-first conversation, adapted Indian-language explanations, simulations, LMS integrations.
  • What only you can arrange: 2–3 pilot educators, one pilot class, a native Hindi reviewer, and consent forms for any learners under 18.

7. Decisions needed now

  • Server: buy the VPS (AWS Lightsail Mumbai or DigitalOcean Bangalore, 2–4 GB) when you're ready to start phase 0.
  • Pilot partners: which school, NGO or educators you can approach first. This decides which subject goes into the test set first.
  • Grant timeline: the submission date and what the funder requires (a working demo, pilot data, or a plan only). This decides how far to get before submitting.
